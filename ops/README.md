# Сборщики и мониторинг kolvrt

Общая панель: `http://192.168.68.60/`, страницы `/wildrift` и `/tver-journey`.
Панель доступна в LAN, привязана только к адресу хоста. HTTP API `/api/status`
позволяет только чтение. `/tver-journey` отдаёт исходный интерфейс обходчика из
`/opt/tver-journey-dashboard` и использует его же функцию подготовки состояния.
HTML/CSS/JS обходчика не копируются и не изменяются на диске; пути ресурсов
и общая шапка адаптируются при HTTP-ответе. Все страницы используют исходный CSS
обходчика как общую основу оформления. Сборщик `tver-dashboard-collector.service` сохраняется.
Веб-процесс один — `kolvrt-monitor.service`; отдельная служба на 8787 удалена.
SSH-псевдоним `kolvrt` не является DNS-записью. Если LAN DNS или hosts сопоставляет
`kolvrt` с `192.168.68.60`, можно пользоваться `http://kolvrt/`.

## Исполнение

Одинаковый `scripts/scrape-worker.mjs` работает в Docker на kolvrt и в Actions.
`wildrift-scraper.timer` проверяет расписание каждую минуту; за одну проверку
выполняется одна готовая задача, затем приоритеты пересчитываются.

| Задача | Расписание МСК | Резерв |
| --- | --- | --- |
| stats | каждый час :17 | два часа после последней успешной проверки |
| riftgg | ежедневно 06:20 | два часа после пропущенного планового запуска |
| guides | воскресенье 07:17 | два часа после пропущенного планового запуска |
| patch-notes | ежедневно 08:41 | два часа после пропущенного планового запуска |

Actions проверяет общий сбор в :07/:37, патчноуты в :12/:42. Его cron может
задержаться; два часа — порог допустимости резервного запуска, а не гарантия
точного времени старта. Ручные полные запуски и обновление патчноутов после API
Pipeline могут выполняться сразу. Выборочный запуск по slugs не обновляет время
успеха всей задачи. Проверка CN-статистики по источнику остаётся независимой в Actions.

`scrape_job_state` и `scrape_runs` хранятся в существующей **продовой** БД.
Рабочие данные и изображения пишутся в прежние продовые PostgreSQL/S3.
Dev PostgreSQL/S3 не участвуют в продовом расписании.

Общая session advisory lock сериализует все импорты, поскольку они могут менять
каталог чемпионов. Проверка срока и запись запуска выполняются под этой блокировкой.
Heartbeat обновляется раз в 10 секунд. При потере связи исполнитель прекращает
дочерний процесс; watchdog срабатывает через 30 секунд без подтверждения heartbeat.
Незавершённая запись защищена дополнительной арендой 90 секунд. Следующий исполнитель
помечает истёкшую запись прерванной. TCP keepalive и ограничение времени незавершённой
транзакции освобождают сессии после разрыва соединения. Ошибка не обновляет успех;
отсутствие новых данных после успешной проверки обновляет. Повтор ошибки — не чаще
раза в 15 минут. История хранится 90 дней, последняя запись каждой задачи сохраняется.

## Размещение и доступы

- `/srv/services/wildrift-worker`: Compose, версия образа и `secrets/worker.env` с существующими доступами.
- `/srv/data/wildrift-worker/status.json`: публичный для локальной панели снимок.
- `/srv/services/kolvrt-monitor`: Python HTTP-сервер, статические файлы и реестр страниц.
- `wildrift-monitor.timer`: обновляет снимок тем же аккаунтом БД, с read-only настройкой сессии.
- Сборщик: максимум 2 CPU / 2 GiB, read-only root, временные файлы в tmpfs.
- Наблюдатель: 0.25 CPU / 128 MiB. Панель: DynamicUser, 128 MiB / 25% CPU.
- Веб-панель читает только снимок JSON и не получает доступы PostgreSQL/S3.

Существующая `wildrift-monitor.service` запускает `observe.py`: он собирает снимок
через контейнер, добавляет состояние systemd и атомарно публикует JSON. Веб-процесс
не вызывает systemd или Docker. При ошибке сохраняется прежняя история с исходным
временем получения и явной отметкой об ошибке; состояние процессов имеет отдельное время.

Используются прежние `DATABASE_URL` и `S3_*` из работающей конфигурации импорта.
Новые роли БД, пароли, S3-ключи и ключи шифрования не создаются. Значения доставляются
на kolvrt через существующий SSH-доступ в `/srv/services/wildrift-worker/secrets/worker.env`
(root, 0600; каталог 0700). Шаблон имён — `wildrift-worker/worker.env.example`.
Не переносить весь env сайта: нужны только указанные параметры БД и S3.
Наблюдатель использует тот же файл; read-only ограничение его сессии предотвращает
случайную запись, но не является изоляцией аккаунтов.

`GUIDES_SYNC_SECRET`, которым домашний генератор диалогов обращается к API,
остаётся прежним. Это HTTP-авторизация, а существующие CLI скрапперов подключаются
напрямую к PostgreSQL/S3. Полного HTTP API для замены этих подключений сейчас нет.

GitHub variables `KOLVRT_PRIMARY_ENABLED`, `KOLVRT_API_REF`, `KOLVRT_UI_REF` не секреты:
первая переключает расписание и позволяет откат, две остальные закрепляют версии
кода kolvrt и резерва. При включённой схеме refs должны быть полными commit SHA.

## Установка, переключение и обновления

Обычная установка `sudo python3 ops/install-kolvrt.py` обновляет только общую панель.
Она не создаёт каталоги или units сборщика. При первом переносе старой панели
проверить `/tver-journey/`, её ресурсы и `/tver-journey/api/status`, затем отключить
`tver-dashboard-web.service` и удалить его unit. Исходные файлы и collector оставить.

Следующие шаги относятся к отдельному внедрению сборщика с продовыми доступами:

1. Проверить исходники, тесты и собрать образ из чистых версий обоих репозиториев.
   Базовый Node закрепить digest через `--build-arg NODE_IMAGE=...@sha256:...`.
2. `sudo python3 ops/install-kolvrt.py --worker` подготавливает выключенные units, **не включает** сбор.
3. Доставить существующие prod-настройки БД/S3 через SSH в `secrets/worker.env`.
   С тем же `DATABASE_URL` выполнить `node scripts/setup-scrape-state.mjs` между запусками:
   команда создаёт только таблицы координации, сохраняет историю и не меняет аккаунты.
4. В `.env` Compose задать `WORKER_IMAGE` точным ID образа и `SCRAPE_REVISION`.
5. Проверить доступы read-only командой `docker compose run --rm worker --check-only`.
6. В GitHub variables закрепить `KOLVRT_UI_REF` и `KOLVRT_API_REF` теми же коммитами.
7. Дождаться завершения старых импортов. Поставить `KOLVRT_PRIMARY_ENABLED=true`,
   затем включить `wildrift-scraper.timer` и `wildrift-monitor.timer`. Проверить
   успешный полный прогон и резервный guard, который пропускает свежую задачу.

До включения переменной действуют прежние сборщики. Новые cron-проверки пропускаются.
При обновлении собрать новый образ, проверить его и согласованно обновить закреплённые
GitHub refs и `.env` на kolvrt между запусками. Запуск патчноутов после API deployment
проверяет совпадение API SHA с закреплённой версией; при несовпадении сообщает ошибку
до импорта. Сначала обновить образ и refs, затем повторить запуск. Журнал хранит
SHA фактического checkout. Автоматического `git pull` внутри
сборщика нет. Права существующего аккаунта импорта не меняются.

Откат: сначала `systemctl disable --now wildrift-scraper.timer` и
`systemctl stop wildrift-scraper.service`, убедиться, что активных импортов нет;
потом установить `KOLVRT_PRIMARY_ENABLED=false`. Старые расписания возобновятся.
Данные и таблицы истории сохраняются. Не удалять общие Docker volumes.

## Проверки

```sh
systemctl status wildrift-scraper.timer wildrift-monitor.timer kolvrt-monitor
journalctl -u wildrift-scraper.service -n 60 --no-pager
curl --fail http://192.168.68.60/api/status
```

В панели отдельно показаны возраст снимка, служба, последний успех и текущий процесс.
Исторический успех не доказывает, что процесс работает сейчас. Если prod-БД недоступна,
устаревший снимок помечается явно. При отключении kolvrt сама LAN-панель недоступна;
резерв и его журнал остаются доступны на GitHub.

Новые страницы добавляются через `kolvrt-monitor/services.json` и адаптер снимка
в `monitor.py`; веб-процесс не получает доступ к управлению приложениями.

Тесты: `node --test test/scrape-*.test.mjs`, `python3 ops/kolvrt-monitor/test_monitor.py`.
Интеграционный тест требует `SCRAPE_TEST_DATABASE_URL` на loopback-базу `wildrift_dev`
и создаёт/удаляет только собственную временную схему. CI запускает его в отдельном PostgreSQL.
